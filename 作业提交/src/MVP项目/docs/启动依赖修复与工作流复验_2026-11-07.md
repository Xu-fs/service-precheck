# 启动依赖修复与业务工作流复验

用户本轮仅需本地业务流程演示，无需接入模型或人工智能助手服务。

## 原因与修复

提交副本已有虚拟环境，但缺少FastAPI等运行依赖。使用该副本的解释器安装requirements.txt后，实际检查进一步发现SQLAlchemy异步模块缺少greenlet。主项目及提交副本的依赖声明统一改为`sqlalchemy[asyncio]>=2.0,<3`，按官方异步安装方式补齐依赖。参考[SQLAlchemy安装说明](https://docs.sqlalchemy.org/en/21/faq/installation.html)。

实际使用提交副本的虚拟环境运行`启动网页.bat --check`通过；`python -m pip check`返回`No broken requirements found`。

## 实际流程复验

用提交副本的虚拟环境启动隔离HTTP服务，健康检查通过。Chrome浏览器驱动现有`tests/browser_demo_cases.py`，两个案例均通过办事人提交、窗口补正、审核员及主任两级转派与确认、办事人确认结案。两案例的自动视角切换、暂停继续、刷新续办、独立记录与新建保留历史均通过；手机宽度无横向溢出。没有调用外部模型服务。

验证只使用虚构教学数据，不能视为正式行政审批或真实客户验收。原始复验输出保存在主项目已忽略目录`.venv/assignment-qa/snapshot-workflow-browser.txt`。上述成功不改变其他旧问答和知识浏览器套件先前失败的记录。

## 用户演示入口

本地服务首页`http://127.0.0.1:8000/`，手动工单`/my/tickets`，自动演示`/examples/workflow`，工作人员登录`/staff/login`。已新增一对待窗口接手的虚构工单，保留历史记录。办事人账号`demo_citizen`，窗口`demo_window`，审核员`demo_reviewer`，主任`demo_director`；新建示例账号使用既有公开本地演示密码，重复初始化不改旧密码。

副本的`.venv/`是本机工具环境，不进入提交压缩包。归档逻辑已显式排除虚拟环境、缓存和Git目录，避免用户本地安装依赖后重新归档时误打包。
