# 第四批工单闭环实施计划

依据：`设计框架.md` 与用户已确认第四批交接。沿用 SQLite、独立工作人员 JWT、事项范围和 SSR，不新增顶层目录，不触及未授权外部接口。

## 接口契约

新增 `infrastructure/ticket_repository.py` 的 `TicketRepository(engine, calendar=None, clock=time.time)`，独立 schema 版本，初始化在既有身份表之后。所有时间为 UTC 时间戳，展示和日界线使用 Asia/Shanghai。

- `initialize()`；`create(user_id, data)`；`citizen_list(user_id, filters={})`；`citizen_detail(user_id, id)`。
- `citizen_action(user_id, id, action, data)`，action 为 `message` 或 `confirm`。
- `staff_list(identity, filters={})`；`staff_detail(identity, id)`；`assignees(identity, matter_id, ticket_id)`。
- `staff_action(identity, id, action, data, transfer_id=None)`，action 为 `accept / transfer / transfer_accept / transfer_reject / transfer_cancel / reply`。
- `notifications(user_id)`；`read_notification(user_id, id)`；`run_due()` 返回执行任务数量。

创建字段：matter_id/scenario_id/title/content/idempotency_key，可选 conversation_id/message_id（必须本人且事项一致；不扩大原会话访问）。不接收伪造预检/正式办件编号。动作必须 expected_version、idempotency_key；回复另含 content/kind（supplement/result），转派含 target_user_id/target_role/reason，拒绝或撤回含 reason。

工单字段：id（TK-uuid）、user_id、matter_id、scenario_id、title、content、status（queued/processing/waiting_citizen/closed）、owner_id、owner_role、version、created_at、accept_due、first_reply_due、first_reply_at、round_no、last_staff_reply、close_due、close_reason、calendar_snapshot、conversation_id、message_id；precheck_id/formal_case_id 固定 null。详情返回 ticket/messages/transfers/transitions；列表 items/total/page/pages，SQL先筛授权后分页。消息 content，转派 status pending/accepted/rejected/cancelled。列表不返回正文。

窗口可看本事项公共队列并接手；详情仅处理人/待接收人/历史参与人且当前岗位仍有本事项权限。热线仅问题、进度、答复摘要；工程师无正文。转派目标必须有对应事项处理权限，窗口专业异常交审核员，审核员再分派窗口/审核员；窗口或审核员可手动升级主任。主任仅接收明确升级。候选人不能跨事项拼接权限。

## 工作日历与调度

示例默认周一至周五，无假日，提交当地时刻顺延到下一工作日同一时刻为接手期限；支持非机密客户日历配置路径环境变量，特殊工作日/休息日，工单保存口径快照。连续48小时从创建起固定。回复后第7/14个自然日同一当地时刻提醒，第14天结束（第15天00:00）关闭。持久任务与站内消息同事务；补充/确认取消旧轮；任务执行再次核对状态轮次并唯一键去重。
