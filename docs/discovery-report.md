## 需求如何归纳

先从已采集事实形成问题假设，再约定业务结果、范围、失败控制和验收。缺少的来源标记待补，不能把六人访谈完整率当作四来源收敛或需求确认。

### 业务流程拆解

要回答：问题发生在哪一步，为什么要这样划分智能体？

1. 先画人工现状泳道，写出触发、输入、8–15个处理步骤、交接和异常。
2. 区分判断点与执行点；按使用的数据、权限、模型能力与失败方式组合执行步骤。
3. 在不可逆动作前设置确定性校验；为低置信、缺资料、冲突和越权安排具名人工接收人。

交付链：现状流程 → 失败方式 → 智能体/工具边界 → 校验与人工升级路径

原文：frameworks/workflow-decomposition.md

### 业务结果与不可逆风险矩阵

要回答：多个需求中，先做哪个最小可验证方案？

1. 列出3–5个候选切入点，分别说明改善的业务结果、现状基线和投入。
2. 评估失败何时被谁看见、能否在损害前拦截、是否可以撤销；不要把模型置信度等同于业务风险。
3. 优先选择高价值、可拦截且可恢复的切入点；高风险需硬约束和责任人否决权，价值或风险未知先补证据。

交付链：候选方案 → 价值/风险比较 → 选择与暂缓理由 → 验收指标与停止条件

原文：frameworks/outcome-risk-matrix.md

### 四来源收敛

要回答：谁说要做，哪里真的坏了，范围允许什么，技术是否可行？

1. Buyer：核实业务目标、预算、优先级和决定权；Operator：用最近一单还原真实操作和失败位置。
2. Brief：核对书面目标、范围、时间和排除项；Industry：寻找可比技术实践，并核实本项目的数据与接口差异。
3. 检查四个视角是否指向同一瓶颈。分歧保留在问题清单：一线帮助定位故障，决策者确认价值，Brief约束范围，行业证据帮助判断可行性。

交付链：四视角陈述与来源 → 收敛/分歧 → 待核实问题 → 有边界的需求假设

原文：frameworks/4-source-convergence.md

### 从证据到候选需求

- REQ-1 清单版本与字段口径统一是预检前置需求
  依据：government-service-f10、government-service-f31、government-service-f30、government-service-f02
  推导：线上清单与窗口要求不一致（f10），事项编码不同步、材料有效期与补正时间缺字段（f31），业务状态无统一视图（f30）。若口径不统一，预检与解释一致率99%（f02）无法达成；但差异完整范围尚未核实，属推断。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：先做字段级比对与接口清单盘点，确认以哪个系统事项编码为主键、缺字段由谁补录；以两类非紧急事项为样本，人工核对清单解释一致率基线，再定集成优先级。
- REQ-2 预检建议须带原记录引用与人工兜底
  依据：government-service-f15、government-service-f44、government-service-f32、government-service-f40
  推导：建议须显示对应原记录和待确认字段，异常时暂停建议由审核员核对，错误不覆盖原记录（f15）；四类异常须转人工并标注触发原因、接手人、确认时间（f44）；接口只读、不自动作行政决定（f32）。这构成不可逆风险防线，但误判责任归属尚未核实。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。
  下一步：在历史资料回放中验证四类兜底触发是否可识别、留痕是否可重建；明确误判责任岗位与暂停复盘流程，由监督员确认后进入并行试点。
- REQ-3 跨岗交接以接手人确认为责任转移点
  依据：government-service-f23、government-service-f25、government-service-f20
  推导：交接须含业务编号、版本、状态、未解决事项与接手人，对方确认才结束待办（f23）；跨岗不能只写已转交，须明确下一责任人（f25）；退回原步骤须保留原因（f20）。但该口径是否作为统一规则尚未与监督员核实。
  判断：候选需求；需用结果与不可逆风险矩阵比较，P0/P1/P2不等于已完成价值风险评分。

  推导：窗口看完整、科室看有效、热线看送达，三套口径混统会重复计算（f50、f53）；须固定分母、排除规则与统计周期，不能用通知数量代替完成量（f51、f53）。基线仅每日600件咨询、约8人时核对（f12、f51），不等于验收样本。
