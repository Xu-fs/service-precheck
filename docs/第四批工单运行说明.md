# 第四批：人工工单闭环

第四批提供真实的本地SQLite工单闭环，不代表真实政务接口接入。材料上传、OCR、预检引擎、正式办件及短信仍未实现。只输入虚构教学资料。

## 启动和使用

沿用README环境及前三批账号工具，Python 3.11+，本机已验证环境为Python 3.12。无需新增依赖。配置仓库外持久目录 `ZHENGWU_RUNTIME_DIR` 和至少32字节 `ZHENGWU_STAFF_JWT_SECRET` 后，执行：

```powershell
$env:PYTHONPATH = (Resolve-Path src).Path
.\.venv\Scripts\python.exe -m zhengwu_precheck.main
```

办事人先在 `/` 登录维护人员创建的独立账号，再进入 `/my/tickets`。公开咨询仍无需登录。工单页面支持提交、查看自己的往来记录、补充问题、确认解决及标记站内消息已读。无依据聊天回答的按钮会引导到真实工单入口；不自动把匿名记录认领为个人记录。API可选关联本人相同事项及情形的已确认咨询与消息，但不会将完整原会话授权给工作人员。

窗口在 `/staff/tickets` 接收本事项公共队列，可筛“我的工单”“待接收转派”及处理状态。接手后在详情回复或选择接收人转派。专业异常先交业务审核员，再由审核员分派实际处理人；升级主任必须手动选择。接收人确认前原责任人继续承担待办，拒绝及撤回保留原因。主任仅处理明确交给自己的升级工单，不获得全部工单权限。

工单岗位授权沿用 `scripts/staff_access.py`，具体参数见[后台运行说明](工作人员后台第一批运行说明.md)。窗口、审核员仅访问授权事项及实际处理关系的工单（窗口可访问公共队列）；热线只看问题、进度及答复，无内部转派原因与原会话链接；平台工程师不能查看工单。混合岗位不能绕过处理关系。材料附件没有开放，不提供证件原图按钮或公开下载链接。

后台使用SSR原生表单，无JS也能完成操作；办事人JS提供提交状态和重复点击防护，禁JS可用原生表单。页面所有动态内容按文本转义。状态冲突会返回统一中文错误，刷新核对新状态后再操作，不自动覆盖他人结果。

## 时限口径

- 接手：教学默认周一至周五，无节假日，提交后下一工作日同一上海当地时刻截止。例如周五10:00提交，周一10:00截止。这是明确的教学口径，真实客户工作时段/节假日待核实。
- 首次答复：提交起连续48小时，包含周末节假日；接手、转派与补充不重置。超时留痕，不自动升级主任，不保证问题已经解决。
- 工作人员两种答复（补充请求/处理结果）都开始新的14天等待轮次；第7天与第14天同一上海时刻各站内提醒一次；保留至第14天结束，即第15天00:00关闭。
- 办事人在截止前补充，会停止当前轮次，并取消尚未生成的本轮提醒/关闭任务。已送出的通知保留。下一次工作人员答复重新完整计时。
- 本人确认记录为 `confirmed_resolved`；日终超时默认完成记录为 `default_complete`。默认完成、通知生成、已读、本人确认分开保存，不能将默认完成宣称实际问题已解决。

可用 `ZHENGWU_WORK_CALENDAR` 指向非机密JSON工作日历文件，启动时读取，例：

```json
{"name":"教学调休样例，非真实客户日历","holidays":["2026-11-02"],"workdays":["2026-11-01"]}
```

特殊工作日优先于周末；同一天不能同时定义工作日与休息日。工单保存创建时日历快照与实际接手期限，后续改配置不会改写历史期限。所有调度时间保存UTC时间戳，显示及自然日界线按Asia/Shanghai（当前UTC+8）。

## 持久化、迁移和编号

新增 `ticket_schema_versions` 版本1，不覆盖旧会话/用户/知识/提示词表。`tickets` 保存归属、责任、固定期限、等待轮次、并发版本与完成原因；`ticket_messages` 保存往来；`ticket_transfers` 保存转派；`ticket_transitions` 及既有 `audit_logs` 追加流转留痕；`ticket_notifications` 保存站内通知和首次已读时间；`ticket_jobs` 保存待执行任务；`ticket_operations` 保存操作者隔离的幂等结果。

人工工单编号为 `TK-UUID`。`precheck_id` 与 `formal_case_id` 为null，数据库约束也不允许填入假记录。关闭仅改工单状态，不删除材料或原始记录，不套用统一90天留存。

接手/转派接收/消息/新轮次任务/通知均在短事务中处理。SQLite先取写锁，再核对版本与状态；多人抢接或接收/撤回冲突只允许一个结果。重复请求沿用相同幂等键及载荷；授权降级后不能回放旧完整快照；已转出责任的旧写操作重试会拒绝，需刷新确认实际结果。

应用生命周期每5秒触发数据库任务检查，不依赖网页开启。任务、轮次和去重键持久化；通知与任务done同事务提交，崩溃回滚后可恢复。执行时重新检查工单状态和轮次。停机跨越第14天时先按截止顺序补提醒再关闭，补充已取消的旧轮次不会恢复。旧轮通知不会被改成“未发送”。

未来迁移其他数据库时，保留 `TicketRepository` 方法边界、幂等唯一键、版本条件更新、责任切换与通知事务；将SQLite写锁替换为行锁/等效并发策略，将同一时间戳排序的rowid替换为显式序列，数据表通过正式迁移保持历史。
