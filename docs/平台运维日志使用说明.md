# 平台运维日志与失败任务

日期：2026-11-01。

## 如何进入

重启网站，在原启动窗口按 `Ctrl+C` 后重新双击 `启动网页.bat`，再用已有工程师账号登录。
工程师工作台包含“系统运行状态”“运行日志与错误查询”“失败任务记录”。既有岗位授权在启动时补入 `system.logs`，无需重建账号。

- `/staff/logs`：按日期、日志级别、错误码、请求编号筛选，支持分页。
- `/staff/failures`：按日期、来源、错误码、任务编号、请求编号筛选，支持分页。
- 对应只读接口：`GET /staff/api/system/logs`、`GET /staff/api/system/failures`。

所有时间按北京时间显示。结束日期包含当天。`page` 默认1，`page_size` 默认25、最大100；错误筛选参数返回422与 `INVALID_LOG_FILTER`。
请求编号与任务编号均使用完整UUID。问答请求编号关联同一轮回答，幂等重放可能对应多条HTTP记录；任务编号匹配单项任务。

## 怎样排查

1. 在“运行日志与错误查询”选择“错误”，确认错误码、路由、时间和耗时。
2. 从错误响应的 `error.request_id` 或 `X-Request-ID` 响应头获得请求编号，粘贴查询。
3. 在“失败任务记录”找到对应问答或知识处理任务。问答任务可点击请求编号跳转关联运行日志。
4. 根据错误码检查模型服务、文档处理配置或后台工作进程；本次提供只读记录，任务重试仍沿用原有业务入口。

流式问答在HTTP头返回后仍可能发生模型超时。此时运行日志的HTTP状态为200，但级别为“错误”、错误码为 `MODEL_TIMEOUT`，请求编号与SSE错误事件及失败问答任务一致；不能只按HTTP状态判断回答成功。

未捕获的服务异常使用通用 `UNHANDLED_ERROR` 响应，正文不会包含异常详情；响应头和JSON都给出 `X-Request-ID`/`error.request_id`，可直接用于日志查询。

## 记录来源与保存

运行日志保存到当前 `ZHENGWU_RUNTIME_DIR` 指定目录内的 `chat.sqlite3` 的 `system_logs` 表；未设置时沿用系统临时目录下的 `zhengwu-web`。数据库初始化只增加表和索引，不替换既有业务资料。

- HTTP记录：服务端生成的请求编号、路由模板、方法、HTTP状态、处理耗时和内部错误码。等待流式响应结束后落库，静态资源请求不记入此表。
- 生命周期：服务成功初始化及正常停止的时间；启动失败和进程突然退出仍需查看启动控制台。
- 失败任务：问答消息的失败状态、知识处理队列的失败状态及后台工作进程异常。已有失败消息和知识任务也可查询。
- 知识处理失败同时留下技术错误日志，失败任务列表以队列当前状态为准，避免同一任务重复展示。
- 工单后台异常记录表示一次工作进程执行出错；原队列仍保持待处理，不能据此认定某张工单已永久失败。记录不包含具体工单正文或内部转派原因。

问答任务时间使用任务创建时间，知识任务优先使用完成时间，后台异常使用观测时间。问答已取消状态不列入“处理失败”。

运行日志每次写入时轮转，保留近30天且最多20000条；只清理 `system_logs`，不清理业务表、审计表或原始资料。失败任务的业务状态不受日志轮转影响，后台异常历史受轮转限制。更新之前的HTTP请求无法补记。

普通日志不保存请求或响应正文、查询参数、凭证、IP、文件名、账号、证件或异常堆栈。工程师新入口只授予 `system.logs`，业务材料和对话正文权限保持原分工。

日志与业务数据库共用SQLite。数据库不可用时无法持久化新日志，控制台输出固定码 `SYSTEM_LOG_WRITE_FAILED`，原请求的结果不被日志写入异常替换。日志页也依赖数据库恢复。现有Uvicorn控制台输出继续保留，和本次新增结构化日志是不同来源。
